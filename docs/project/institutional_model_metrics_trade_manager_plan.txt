Developer Task: Add Institutional Model Metrics Tracking + Trade Manager Behavior Envelope

Objective:
Implement a metrics and monitoring layer that grades every model after robustness testing and continuously monitors live/paper/shadow behavior against expected bounds. This is not a redesign of the research pipeline, robustness engine, execution engine, or trade manager. Add a clean, versioned measurement layer that plugs into the existing backtest, robustness, portfolio, and live-monitoring flows.

Core Principle:
Robustness testing qualifies the model. The trade manager governs the model. Every promoted model must produce a model scorecard and a model behavior envelope that can be monitored in live/paper/shadow mode.

Do not remove existing functionality. Do not change existing model logic unless required to expose metrics. Do not hardcode for one symbol or one asset class. This must work across equities, options, futures, crypto/BTC, and prediction-market forks where applicable.

4. GREEN / YELLOW / RED MODEL STATE ENGINE
============================================================

Implement a live model-state engine for the trade manager.

Every active model must be classified as:
- GREEN: behavior inside expected bounds
- YELLOW: degraded but not failed
- RED: outside allowed bounds; reduce, pause, or kill according to policy

Required state checks:

GREEN state:
- PnL inside expected distribution
- drawdown inside normal range
- trade frequency normal
- slippage normal
- fill rate normal
- latency normal
- signal distribution normal
- feature values inside training domain
- approved regime active
- correlation to active book acceptable
- no abnormal data-quality warnings

YELLOW triggers:
- drawdown approaching warning band
- slippage above normal but below kill threshold
- fill rate weakening
- trade count materially above or below expected
- signal distribution drift
- feature drift near boundary
- confidence rising while realized accuracy falls
- correlation to other models increasing
- latency nearing alpha half-life
- regime uncertainty
- defensive overlay blocks increasing
- rolling win rate below expected range but sample size still small

RED triggers:
- drawdown breaches kill threshold
- live PnL breaches historical 99% adverse envelope
- slippage exceeds max allowed slippage
- execution latency exceeds alpha half-life
- fill quality collapses
- feature values outside training support
- model trades in blocked regime
- alpha inversion: strongest signals lose more than weak signals
- high-confidence predictions become systematically wrong
- trade frequency explodes or drops to zero abnormally
- data feed stale or conflicting
- order reject rate abnormal
- correlation spike creates portfolio-level concentration
- defensive model repeatedly blocks but alpha model keeps firing
- model behavior statistically inconsistent with robustness/OOS expectations

State actions:
- GREEN: allow normal operation
- YELLOW: reduce size, raise signal threshold, reduce frequency, increase monitoring
- RED: pause new trades, flatten or reduce according to risk policy, generate incident report, require review before reactivation

Do not make the state engine discretionary. It must be rule-based, auditable, and replayable.

============================================================
8. SCORING SYSTEM
============================================================

Add a weighted institutional model grade.

Default weights:
- Net Alpha Quality: 20%
- Drawdown / Tail Risk: 20%
- Robustness Stability: 20%
- Execution Realism: 15%
- Portfolio Contribution: 15%
- Live Behavioral Control: 10%

Each category should produce:
- raw metrics
- normalized score
- pass / warning / fail
- explanation
- sample size warning if unreliable

Final model grades:
- A: production candidate
- B: paper/shadow candidate or limited capital
- C: research only
- D: reject
- F: invalid / failed / non-reproducible

The grade must not be based on Sharpe alone. Penalize:
- high drawdown velocity
- unstable folds
- high slippage sensitivity
- poor capacity
- low sample size
- poor calibration
- concentrated return source
- high correlation to existing models
- alpha inversion
- excessive parameter sensitivity
- unrealistic execution assumptions
