# Rule 536.B Timestamp Gap — Known Defect and Remediation Plan

**STATUS: DRAFT — owner and compliance review required before any shadow or
live activity that generates order records.**

Plan reference: WS-0 (compliance pre-work), options lane pre-arm checklist
Date drafted: 2026-06-12
Regulation: CME Rule 536.B (order-record keeping — timestamp requirements)
Cross-reference: specs/OPTIONS_LANE.md ledger entry o-h

---

## Regulation Summary

CME Rule 536.B requires every order entered or transmitted by a member or
participant through an automated system to be accompanied by a time-stamp
recording when the order was entered or transmitted, expressed to the
granularity required by the exchange (currently milliseconds for most CME
Globex instruments; consult the current Rule 536 text for the operative
granularity floor at time of review). Orders subject to Rule 536 must be
retained for a minimum of five years and must be producible on demand to
the exchange or relevant regulators.

The operative requirements for this gap are:

1. **Wall-clock (epoch) timestamps** synchronized to a reliable time source.
   Monotonic clocks that are not wall-synced do not satisfy the rule's
   requirement to know *when* an order was placed in calendar time.
2. **Dual-stamp discipline** (recommended best practice): one timestamp at
   order creation (wall-clock epoch, synced), one timestamp at first
   transmission or modification, enabling reconstruction of order latency.
3. **Five-year retention** of all order records with their timestamps in a
   form reproducible on demand.

## The Gap: `trade_manager/manager.py` Monotonic Timestamp

The method responsible for generating automatic order-transition timestamps is:

```python
# packages/trade_manager/manager.py, lines 585–590
@staticmethod
def _automatic_transition_timestamp(previous: TradeManagerOrderTransition | None) -> int:
    now_ns = time.monotonic_ns()
    if previous is not None and now_ns < previous.timestamp_ns:
        return previous.timestamp_ns
    return now_ns
```

**Line numbers verified against the branch as of 2026-06-12. The method is
`_automatic_transition_timestamp`, defined at line 585 and returning at
line 590. The plan text cited lines 586–590; the actual method body spans
585–590 including the `@staticmethod` decorator line at 585.**

### Why this is a gap

`time.monotonic_ns()` returns a monotonic counter whose epoch is
implementation-defined and is NOT synchronized to wall-clock time (UTC or
local). The Python documentation explicitly states: "The reference point of the
returned value is undefined, so that only the difference between the results of
consecutive calls is valid." On CPython/Windows this is typically derived from
`QueryPerformanceCounter`, whose epoch is system boot time, not the Unix epoch.

A timestamp produced by `time.monotonic_ns()` therefore:

- Cannot be interpreted as a wall-clock time without an offset derived from
  a separate monotonic↔wall-clock pairing measurement.
- Will produce order records whose "time of order entry" cannot be expressed
  in calendar time without additional reconstruction.
- Does not satisfy the Rule 536.B requirement that records be timestamped with
  the calendar time of entry/transmission.

The gap affects all order-transition records generated by `TradeManager` that
call `_automatic_transition_timestamp` — which includes the primary order-state
machine path for new orders, modifications, and cancellations.

**Phases 0–1 (this branch, research/backtest only):** No live or shadow orders
are placed. No order records subject to Rule 536.B are generated against
exchange order IDs. The gap is NOT an active compliance violation in this phase,
but it is a known defect that blocks any transition to shadow or live trading.

**Phase 2 (shadow trading with order records):** If any order records are
generated that associate a monotonic timestamp with a Rithmic-assigned order ID
against a CME instrument, those records are non-conformant under Rule 536.B.
Shadow trading must NOT begin until the dual-stamp remediation is in place.

## Remediation Plan

The remediation requires the following changes, targeted for Phase 2 (before
any shadow activity with order records):

### Step 1: Wall-clock + monotonic pairing at session start

At session initialization, record a pairing:

```python
import time

_wall_mono_offset_ns: int  # to be captured at session start

def _capture_wall_mono_pairing() -> int:
    """Return (wall_ns - mono_ns) offset at capture time."""
    wall_ns = time.time_ns()
    mono_ns = time.monotonic_ns()
    return wall_ns - mono_ns
```

This offset allows any monotonic timestamp to be converted to an approximate
wall-clock timestamp: `wall_ns = mono_ns + offset`. The offset should be
re-captured periodically (e.g., at each session reconnect) to bound clock drift.

### Step 2: Dual-stamp on order records

Modify `_automatic_transition_timestamp` (or its callers) to produce a
dual-stamp record:

```python
@dataclass
class DualStamp:
    mono_ns: int   # time.monotonic_ns() — for latency decomposition
    wall_ns: int   # derived from mono_ns + session-start offset — for Rule 536.B
```

Both values must be stored in the order-transition record. `wall_ns` satisfies
Rule 536.B; `mono_ns` is retained for latency attribution and should not be
deleted as it enables post-hoc decomposition.

### Step 3: NTP/PTP synchronization check at session start

Before opening any order channel, assert that the system clock is synchronized
to a reliable time source (NTP stratum ≤ 2 or PTP). On Linux: check
`chronyd tracking` or `timedatectl show`. On Windows: check `w32tm /query /status`.
Log the measured clock offset. Reject session start if offset exceeds an
operator-set threshold (e.g., ±100 ms from stratum-1 source).

### Step 4: Five-year retention wiring

Order records with dual-stamps must be written to a retention store (append-only
log or equivalent) at write time, not queued to memory. The retention store must
be:

- Append-only (no in-place modification of past records).
- Addressable by order ID and session timestamp for regulator pull requests.
- Retained for a minimum of five years per Rule 536.B.

Retention store design is a Phase 2 deliverable. The in-memory `TradeManager`
state store in the current codebase does not satisfy this requirement.
