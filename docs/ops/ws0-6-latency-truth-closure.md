# Rithmic live (R|API+) infrastructure and order-ack latency evidence: Aurora hosting, routing path, conformance, and expected live ack bounds for a CHI404 colo client

*Generated 2026-06-12 by WS-0 research workflow (web sources; verify before contract decisions).*

## Findings

- Rithmic's live order infrastructure sits INSIDE the CME Aurora data center: Rithmic's hosting affiliate TheOmne.net, LLC operates 'Data Center 04 - located in the CME's data center in Aurora, Illinois' and 'is the home to Rithmic's R|Trade Execution Platform'; its second site, Data Center 01, is in the Telx meet-me area at 350 E Cermak Rd, Chicago [1][2]. CME's matching engine is in CyrusOne Aurora I (2905 Diehl Rd, Aurora) [12].
- TheOmne.net dedicated servers (RHEL or Windows Server, 1Gb/10Gb) 'can be connected directly to Rithmic's market data and trading network' and 'subject to exchange approval these machines may be connected directly to our exchange facing routers (10Gb ports)' — i.e., a colo client can cross-connect straight into Rithmic's order path within the CME Aurora building [2].
- Order routing path (official statements): standard R|API+ -> Rithmic OMS/ticker plant (R|Trade Execution Platform) -> Rithmic 'exchange facing gateways' which evaluate FCM-set pre-trade risk -> exchange (CME iLink). R|Diamond API bypasses the OMS/ticker plant: it 'connects directly to Rithmic's exchange facing gateways and market data handlers'; orders can rest pre-risk-checked at the gateway and be released with a small message [7][9].
- Rithmic's only published latency number is for Diamond, not R|API+: 'transit times... of less than 250 microseconds' tick-to-trade, requiring Aurora colocation, C++/Linux, and effectively DMA-scale setup (forum: 'you won't get 250us unless you are in Aurora, and even then... only on Rithmic's private Diamond API... huge bankroll, iLink, DMA, dedicated risk management') [7][8][6].
- Rithmic representative public post (Elite Trader 'CME roundtrip question', ~2014, quoted on futures.io): TCP acks across Rithmic's tap between Rithmic routers and CME routers measure '15-16 microseconds, very consistently'; '500 microseconds from the release of an order to the exchange by our software until receipt of a fill/ack does not seem very slow (though you were able to realize less than 375 microseconds)'; the quoting user measured 500-5,000 us round trips through Rithmic from Aurora, variability attributed to exchange workload [4][5].
- Rithmic OMS internal order-processing variance reported as 0.5 ms to 1.5 ms depending on order complexity and system load (Optimus Futures community thread with Rithmic input); same thread: Diamond <250us, market data publication delays up to 14 ms during NFP-class events [3].
- Forum-measured live figures from Aurora/CME-DC VPS with 0.35 ms pings (futures.io, 'fastest CME retail trading API'): execution component '<1 ms', but Rithmic FEED 3-4 ms mean / 30 ms 97th percentile; user models 50 ms safety margin; rule of thumb in thread: multiply ping by 3-6x for tick-to-confirmed [4].
- Long-running futures.io R|API journal (user 'Ian', updated post): Chicago bare-metal (non-Aurora) gets market data in 2-3 ms and order send 2-3 ms back (~4-6 ms tick-to-trade stable, <10 ms 75%+ of the time target); 1-2 core Aurora VPS ($100-300/mo) 'chokes on heavy load' and runs 1-5 SECONDS behind real time during US cash open; Aurora bare metal costs 3-5x Chicago (~$600/mo total for his 2-server Chicago setup); RAPI delivers all callbacks on a single main thread (latency foot-gun); merging Databento + Rithmic feeds packet-by-packet cut tail latency more than anything else, RAPI kernel-bypass attempt gained ~nothing [6].
- Bound for a CHI404 (Aurora-area) colo client on standard R|API+ live: floor ~0.6-1 ms (0.3-0.7 ms intra-campus network RTT + 0.5-1.5 ms Rithmic OMS+gateway + ~0.2-0.5 ms exchange ack); expected p50 ~1-3 ms, p95 ~5 ms, p99 10-30 ms load-dependent (shared retail-grade Rithmic infrastructure dominates tails). Vs paper 3.5 ms p50 / 6.3 ms p99: live p50 plausibly BETTER than paper (sim acks are generated by Rithmic's SIM engine, not the exchange), but live p99 tails during bursts can be WORSE than paper's 6.3 ms — paper distribution is not predictive of live tails [3][4][6][13].
- Rithmic SIM/paper artifact confirmation: Rithmic states the simulator timestamps orders to the microsecond ('time received by Rithmic' and 'time received by the simulator') but declined to state any fixed added latency; sim order-status messages originate from the SIM engine, not an exchange — use the Recent Orders microsecond stamps to decompose the 3.5 ms paper p50 [13].
- Conformance: R|API conformance test is mandatory before live AND before even the paper-trading API ('in order to use the API in Rithmic Paper Trading, the prospect must first pass conformance'); free limited 'Rithmic Test' environment first, then Paper, then Live — switching is a config/gateway change; docs, libraries and test logins are issued directly by Rithmic after an FCM introduction (e.g., AMP, Optimus); broker-dependent fee described as modest; covers order lifecycle (new/modify/cancel/partial-fill/reject), disconnect-recovery, and risk-limit behavior [14][15][16][3].
- Rithmic running costs (Optimus published): $25/mo minimum connection fee per user ID, $0.10/contract trade routing, ~$100/mo ($99.99) API connection per user ID; TheOmne Aurora VPS marketed at 'tick-to-trade in less than 250us' (Diamond-style marketing claim attached to colocation product) [8][14].
- CME reference figures: median inbound latency 52 us router-to-match-engine and 39 us inbound variability (median vs 95th pct) — from CME's Aug 2012 performance release (pre-iLink3; cite with date caveat) [10]. Modern derived measurements (Mar 2026, 500-event study matching MDP3.0 Trade Summary vs private confirms via CME timestamps): median MSGW confirmation latency 203 us (TransactTime->SendingTime), MSGW beats public market data by 64 us median; Convenience Gateway (CGW) only 16 us ahead and LOSES to public Trade Summary in 11% of cases — relevant since Rithmic's non-Diamond flow is gateway-mediated [11].
- Databento (your existing lake vendor) hosts its real-time CME gateways in CyrusOne Aurora I with 6.1 us median venue-handoff-to-send latency — supports the Ian-style dual-feed merge to de-tail Rithmic market data while keeping Rithmic for order entry [12][6].

## Open questions

- Exact CHI404 facility identity vs CyrusOne Aurora I / TheOmne DC04: is it in-building (cross-connect possible to Rithmic's exchange-facing routers) or a nearby Aurora-campus building adding ~0.1-0.5 ms fiber RTT? Determines whether the 0.35 ms ping forum baseline applies.
- Which Rithmic gateway ('Chicago Area' etc.) a CHI404 client gets assigned over standard R|API+, and whether Rithmic/FCM will permit a direct cross-connect without renting TheOmne hardware.
- No official Rithmic R|API+ (non-Diamond) order-ack SLA or distribution exists publicly — only the rep's 500us/'<375us realized' anecdote (2014) and trader reports; current 2025-2026 numbers under iLink3/MSGW load unverified.
- No current official CME iLink3 in-to-out gateway latency publication; the 52us median inbound is a 2012 figure, and the 203us MSGW median (Mar 2026) is a derived third-party estimate from CME timestamps — true 2026 ack component needs own measurement.
- Whether the 3.5ms paper p50 is Rithmic SIM-engine queueing or WAN/client-side: decompose using R|API order-record microsecond timestamps (received-by-Rithmic vs received-by-simulator) before assuming live will be faster.
- Diamond API qualification thresholds (bankroll, volume, FCM sponsorship, cost) are not public — only forum characterization as out of retail reach; relevant only if the options lane ever needs sub-ms tick-to-trade.

## Recommended actions

- Budget live order-ack for CHI404 R|API+ at p50 1-3 ms, p95 ~5 ms, p99 10-30 ms (burst-dependent); treat paper 3.5 ms p50 as roughly representative-to-pessimistic for live median but treat paper 6.3 ms p99 as NOT representative of live tails — size 0-45DTE ES/NQ options quoting/cancel logic against the 10-30 ms tail, not 6.3 ms.
- Instrument from day one: log R|API order-record microsecond timestamps (Ssboe/Usecs; received-by-Rithmic vs received-by-sim/exchange) to decompose paper 3.5/6.3 ms now, then re-measure the same probes live with small MES/MNQ canary orders before options go-live.
- Ask the FCM + Rithmic three concrete questions during onboarding: (a) assigned order gateway and its physical location, (b) cross-connect options from CHI404 into Rithmic DC04/exchange-facing routers (10Gb port, exchange approval per TheOmne), (c) any current internal ack-latency stats for colocated R|API+ clients.
- Start Rithmic conformance early — it gates even the paper-trading API: request docs/test login via FCM, pass on free 'Rithmic Test' env, exercise full order lifecycle + disconnect-recovery + risk-reject paths that the test (and CME options reality) demands.
- Adopt the dual-feed merge pattern for the options lane: Databento Aurora-I real-time feed merged packet-by-packet with Rithmic R|API+ market data (take fastest), Rithmic for order entry only — public evidence says this cuts tail latency more than any client-side optimization, and avoids Rithmic's 3-4 ms mean / 30 ms p97 feed tails.
- Keep R|API+ callbacks off the single RAPI main thread (queue-and-hop pattern), run Linux for the order path, and avoid 1-2 core VPS sizing — public failure mode is 1-5 s backlogs at US cash open, fatal for 0DTE option quoting around fixings.
